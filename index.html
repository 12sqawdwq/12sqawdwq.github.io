Selected projects

Some are tools, some are experiments, and a few became much larger than I originally expected. These are the ones that best show the questions I keep returning to.

01 / ACTIVE EXPERIMENT · TERMINALS

code-with-pi

I wanted to see what a coding agent was actually doing in the shell without losing state between tool calls.

QuestionCan the agent and user attach to the same long-lived shell instead of observing separate command processes?
ImplementationA C11 broker owns PTY on Linux or ConPTY on Windows; Pi talks to it over authenticated local IPC, and tmux provides the Linux split view.
CheckedTests exercise state persistence, cancellation, transcript replay, resize, large output, installation, and Pi RPC execution.
Repository Architecture notes
02 / RESEARCH CODE · FINITE ELEMENTS

ANSYS Simulation IOP

A finite-element investigation of how eyelid mechanics and measurement geometry affect transpalpebral tonometry.

QuestionWhich probe-response terms remain useful once thickness, material response, alignment, contact, and mesh resolution are varied?
ImplementationParameterized APDL models, staged sweeps, post-processing scripts, run manifests, and data-provenance records.
LimitsThe repository keeps failed extrapolation, unresolved identifiability, and mesh sensitivity visible. It is not a production calibration.
Repository Data provenance
03 / EXPERIMENTAL · CAE VALIDATION

ANSYS_skill

This grew out of a simple problem: a result object can exist in Mechanical even when the result has not actually been solved and evaluated.

QuestionWhat evidence is enough to distinguish geometry-ready, setup-ready, solver-input-generated, and solved/evaluated states?
ImplementationDelivery-file checks, explicit state gates, screenshot examples, a small CLI, and a cantilever reference case.
BoundaryFilesystem checks can reject incomplete handoffs; they do not replace review of contours, numerical values, assumptions, or benchmark error.
Repository Related workflow note

Things I am exploring

These are current questions rather than a finished specialization. I am still figuring out which layer I want to spend most of my time in.

Coding agents and terminals

How should PTY lifetime, process ownership, shell state, monitoring, and human takeover work when an agent is issuing commands?

CAE validation

What evidence distinguishes a configured model from a solved and evaluated one, and which checks can be automated without overstating correctness?

Source-first CAD

How much of an AI-assisted CAD pipeline can remain deterministic, inspectable, and reconstructable before geometry is exported?

Scientific computing

Parameter sweeps, sensitivity, provenance, manifests, failed assumptions, and the point where a result stops surviving validation.

HPC experiments

Dataset splits, training environments, topology, model scaling, and keeping enough run context to explain a result later.

Embedded boundaries

What changes when software meets sensors, timing constraints, native code, communication protocols, and imperfect hardware?

Things I try not to hand-wave.

01

What state the system actually reached

“Created,” “configured,” “solved,” and “evaluated” are different states. I try not to collapse all four into “done.”

02

Where an artifact came from

Inputs, code revisions, environments, run manifests, and generated outputs are much more useful when they can be traced.

03

What a test can actually establish

A screenshot can show UI behavior; it cannot establish numerical convergence or physical credibility.

04

What failed later

Failed extrapolation, sensitivity, and identifiability limits often explain more than a polished success case.

About

I am Ziyu Zhao (Victor), a third-year undergraduate heading into my fourth year in Microelectronics Science and Technology at Xi'an Jiaotong-Liverpool University. I tend to turn small annoyances and open questions into repositories; some remain rough experiments, while others accumulate native code, test scripts, diagrams, and more edge cases than expected.

I use coding agents often as part of development. What interests me is less who typed each line and more how the problem is framed, which mechanisms are chosen, how failures are debugged, and what evidence survives validation. I have not fully specialized yet; so far I keep returning to engineering software, systems tooling, and scientific computing.

Public research includes PAD-Former for PI-RADS classification, finite-element work on transpalpebral tonometry, and medical-audio compression experiments.
